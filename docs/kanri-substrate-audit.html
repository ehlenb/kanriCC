01 / Executive summary

The finding

I queried the live Supabase project (iqotqiqamytpjoafwgzb) for its extension catalogue before searching GitHub, because availability is the binding constraint and everything else is speculation. The result reframes the entire exercise.

Every extension needed for the Wave 1 substrate and the Wave 2 retrieval layer is available and none of them are turned on. Meanwhile Supabase publishes a first-party production blueprint, Automatic Embeddings, that wires exactly these pieces together: insert or update trigger → pgmq queue → pg_cron worker every 10 seconds → pg_net call to a function → write back → delete the job. Failed jobs reappear after the visibility timeout and retry automatically.

That pattern is not "how to generate embeddings." It is the event spine.

Swap the payload and the same machinery runs automatic context refresh, embedding backfill, pre-meeting briefs that fire themselves, and the nightly outcome rollups. Wave 1 and most of Wave 5 share one piece of infrastructure that costs zero new services and is documented by the vendor Kanri already pays.

The contrast with the AI-memory ecosystem is stark. Graphiti (Apache 2.0, 30.2k stars) requires Neo4j, FalkorDB, or Amazon Neptune. Mem0 (Apache 2.0, 63.9k stars) requires a vector database service plus its own LLM extraction pipeline. Letta (Apache 2.0, 24.4k stars) is a server. Kanri is TypeScript on Vercel serverless talking to Postgres. None of the three is a sane dependency, and the best idea in all of them is free to copy.

The second-order finding is Japan-specific and is the most valuable thing in this report after the extension catalogue: Japan has state-provided master data that nobody in this competitive set bothers to wire up. The National Tax Agency runs a free 法人番号 (corporate number) Web-API for company lookup and 名寄せ. The Digital Agency publishes an address base registry behind an MIT-licensed TypeScript normalizer. Neither Spott nor Bullhorn nor Loxo will ever integrate these. They are small, cheap, and unavailable to a horizontal product.

02 / What the ecosystem reveals

Four things worth knowing

Convergence
Bi-temporal fact modelling has won the memory argument

Graphiti tracks four timestamps per fact: when it was created and expired in the system, and the range over which it was actually true. Superseded facts are marked expired, never deleted. On temporal-retrieval benchmarks this approach scores 63.8% against Mem0's 49.0% — a 15-point gap specifically on facts that change over time.

Directly usable
Postgres has quietly become a full retrieval stack

pgvector plus a lexical index plus reciprocal rank fusion now matches dedicated search infrastructure for most workloads, without a sync pipeline. The catch for Kanri is which lexical index — see §11.

Contradicts a Stage 1 plan
Text-to-SQL is not reliable enough for "Ask Kanri"

GPT-4o scores 86.6% on the Spider 1.0 benchmark and 10.1% on Spider 2.0, which uses realistic enterprise schemas. o1-preview reaches 17.1%. The consensus fix is a semantic layer: typed, governed tools the model selects from, rather than SQL it authors.

Free technique
Contextual retrieval is a large, cheap win

Anthropic's method — prepend an LLM-written chunk-specific context before embedding — cuts retrieval failures by 49%, and 67% with reranking. Kanri is unusually well placed: ai_context is the context to prepend, already written and already reconciled.

The general lesson: the open-source ecosystem has solved the architecture questions Kanri faces, and every packaged solution to them assumes a Python service and a dedicated datastore. The leverage is in the patterns, not the packages.

03 / The Stage 1 correction

Postgres full-text search does not work on Japanese

Correction to the Stage 1 report

Stage 1 recommended "pgvector over notes_interview and ai_context, plus Postgres full-text search" as Wave 2. The second half of that sentence was wrong, and I did not check it before writing it.

PostgreSQL's built-in full-text search tokenizes on whitespace and has no Japanese configuration. Japanese does not use spaces between words. Running to_tsvector over 職務経歴書 text or Japanese interview notes produces effectively one enormous token per sentence — the index builds, the queries run, and the results are garbage. This would have surfaced during Wave 2 implementation as an inexplicable relevance failure on exactly the content Kanri cares most about.

The fix is pgroonga, which is available on the project right now. It uses variable-length N-gram indexing, supports all languages including Japanese and Chinese, needs no recheck step, and does not block searches during index updates.

The alternative Japanese approach, pg_bigm, is not in Supabase's catalogue and is slower in any case. The ParadeDB pg_search and TigerData pg_textsearch BM25 extensions that dominate the 2026 hybrid-search literature are both absent from Supabase, so the standard "BM25 + pgvector + RRF" recipe is not directly available. Kanri's hybrid search fuses PGroonga's score with pgvector's cosine distance instead. That is a real design constraint and it should be written down before anyone starts.

05 / Tier 1

Use these — high value, high fit

  1. T1
    The Postgres substrate: pgvector + pgroonga + pgmq + pg_net + pg_cron

    Five CREATE EXTENSION statements and one migration establish the entire Wave 1 and Wave 2 foundation. No new service, no new vendor, no new bill, no new failure mode outside the database Kanri already runs. RLS continues to apply because the data never leaves Postgres — which matters under APPI in a way that shipping candidate text to a third-party vector service does not.

    Recommendation: adopt as the Wave 1 opening move. Caveat: pg_net is fire-and-forget with a default timeout; the queue, not the HTTP call, is the durability guarantee. Never rely on a pg_net response.
  2. T2
    The Supabase automatic-embeddings pattern, generalized

    The published guide solves embedding generation. The identical machinery — trigger enqueues, cron drains, HTTP dispatches, worker writes back and deletes — solves automatic context refresh, which is the single highest-leverage item in the Stage 1 report. Build it once as a generic util.enqueue_job(kind, payload) and both Wave 1 and Wave 2 land on the same rails.

    Recommendation: copy the architecture, not the code. It is a docs page, not a library. Divergence: Supabase assumes Edge Functions; Kanri's handlers live on Vercel. pg_net does not care.
  3. T3
    Contextual retrieval over interview notes

    Before embedding a chunk of notes_interview, prepend a one-line situating context generated from the candidate's ai_context. Anthropic reports 49% fewer failed retrievals, rising to 67% with reranking. Kanri gets this cheaper than most teams because the situating context already exists and does not need to be invented per chunk.

    Recommendation: build into the Wave 2 embedding worker from day one. Retrofitting means re-embedding everything.
  4. T4
    法人番号 Web-API for client identity

    Free application ID from the National Tax Agency. Three operations: look up by number, search by name, fetch changes over a period. Gives every client record a canonical 13-digit identity, resolves 株式会社 prefix and suffix variants, and the period-diff endpoint means Kanri can detect a client company's registered changes without polling anything commercial.

    Recommendation: small, Japan-native, structurally unavailable to a horizontal competitor. Wave 3 or 4. Caveat: read the usage terms before shipping; government API terms are not open-source licenses.
06 / Tier 2

Investigate before committing

  • Japanese embedding model choice. Domain-specific Japanese models beat multilingual ones on Japanese benchmarks — Ruri-base (111M params) reports 71.91% average on JMTEB and outperforms the much larger mE5-large. But Kanri's content is bilingual and often code-switched within a single interview note. A multilingual model that handles both may beat a Japanese-specialist model that handles one. This needs an actual test on real Kanri notes, not a benchmark table.
  • Reranking. Managed APIs (Cohere Rerank 4, Voyage rerank-2.5, Jina v3) are one call and no GPU. Self-hosted cross-encoders are impractical on Vercel serverless. A third option nobody lists: Claude already reranks well when given ~30 candidates and asked to score with reasons — and it produces the explanation that Kanri's explainability rule requires anyway. Test that before buying a reranker.
  • normalize-japanese-addresses. MIT, 960 stars, actively maintained, but it fetches address data from a remote Geolonia endpoint by default. For a serverless handler that is a latency and availability dependency. It can be pointed at local data files — investigate that path before adopting. Underlying data derives from government sources with attribution expectations.
  • keigo_transfer_task as an eval harness. 390 sentences annotated by two native speakers for conversion necessity and type. Small, but the alternative for validating 推薦文 register is asking a human every time. Worth an hour to assess whether it transfers to business-document generation rather than learner correction.
  • rum instead of a plain GIN index. RUM stores positional and timestamp information in the index, which makes recency-weighted text ranking a single scan. Kanri's memory model is explicitly recency-weighted. Possibly a natural fit, possibly overkill next to PGroonga. Benchmark, do not assume.
07 / Tier 3

Learn from, then build it yourself

  1. L1
    Graphiti's bi-temporal fact model

    The most valuable idea in the entire audit. Graphiti gives every fact four timestamps: created and expired in the system, valid and invalid in the world. Superseded facts are marked expired, never deleted, so the graph can answer "what did we believe on 12 June" as well as "what is true now."

    Why this matters for Kanri specifically: refresh-context already produces "salary expectation updated to ¥16M (was ¥14M at registration)" — a bi-temporal fact expressed as English prose. That sentence is generated fresh on every refresh, cannot be queried, cannot be aggregated, and gets truncated at 300–600 characters before most handlers ever see it. The upgrade is not to adopt a graph database. It is to make the reconciled fact a row: subject, predicate, value, valid_from, valid_to, source interaction. Then "which candidates raised their salary expectation this quarter?" becomes a query instead of an impossibility.

    Recommendation: steal the model, refuse the infrastructure. A candidate_facts table in the Postgres you already have.
  2. L2
    Semantic layer over text-to-SQL, for Ask Kanri

    Stage 1 proposed "Ask Kanri" as an agentic endpoint with database tools. The benchmark evidence sharpens what those tools should be. Text-to-SQL against realistic enterprise schemas collapses — GPT-4o falls from 86.6% on Spider 1.0 to 10.1% on Spider 2.0. Pointed at raw tables, a model re-derives joins and grain on every prompt, so the same question returns different answers on different days.

    The fix is a small set of typed, governed tools that encode Kanri's domain — find_candidates(criteria), get_pipeline(client_id), rejection_history(contact_id) — with RLS applied before the query runs. Fewer degrees of freedom, reproducible answers, and an audit trail of which tool ran with which arguments. That audit trail is the explainability panel.

    Recommendation: revise the Wave 6 plan. Never ship raw SQL generation over the recruiting database.
  3. L3
    Mem0's extraction-and-reconciliation loop

    Worth reading for the shape: LLM extracts candidate facts from raw text, embeddings find related existing memories, a second pass decides add / update / supersede. Mem0's April 2026 algorithm moved to single-pass ADD-only accumulation, dropping UPDATE and DELETE entirely and resolving conflicts at retrieval time through temporal reasoning instead.

    That is a genuinely interesting trade and it maps onto a decision Kanri will face: does refresh-context rewrite the note, or does it append facts and reconcile at read time? Append-only is auditable, cheaper to write, and preserves the correction history that §L1 wants. Rewriting is simpler to consume. Kanri currently rewrites.

    Recommendation: read the algorithm, adopt append-only for structured facts, keep the prose note as a generated view over them.
  4. L4
    Letta's self-editing memory blocks

    The concept worth taking is that an agent can hold a small, persistent, editable block of context that it maintains itself, distinct from retrieval. For Kanri the analogue is a recruiter-level memory — how this person works, who they trust, which advice they take — that is separate from candidate and client memory and small enough to include in every prompt. Stage 1 listed this as the fourth and hardest moat layer. Letta shows a working shape for it.

    Recommendation: concept only. The repo is now largely a landing page with active work moved elsewhere.
  5. L5
    Reciprocal rank fusion as the hybrid-search join

    RRF combines two ranked lists by summing reciprocal ranks, needs no score normalization between wildly different scales, and is about fifteen lines of SQL. Given that Kanri cannot use the BM25 extensions the literature assumes, RRF over PGroonga rank and pgvector distance is the practical hybrid. It is a technique, not a package.

08 / Tier 4

Do not use, despite looking relevant

  • Graphiti, Mem0, Letta, or Cognee as dependencies. All Python. All require infrastructure Kanri does not run — Neo4j, FalkorDB, Neptune, Qdrant, or a persistent server. Adopting any of them means running a second backend in a second language to store a memory Kanri already generates better, because Kanri's version knows what a CCM stage is and a generic memory layer never will.
  • JavaScript Japanese tokenizers — kuromoji.js, lindera-js, TinySegmenter, budoux. These solve tokenization in the application. PGroonga solves it in the index, which is where Kanri needs it. Shipping a morphological dictionary into a Vercel function to duplicate what the database already does is cost with no benefit. The one plausible exception is display-layer line breaking, which is cosmetic.
  • Open-source resume parsers. The field has already migrated from spaCy-based parsers to LLM extraction — the most-cited project rewrote itself onto a local Qwen model. Kanri does LLM extraction with Claude today and it works. Adding a parser library would be a downgrade.
  • OpenCATS or any legacy open-source ATS. PHP/MySQL, 2007 lineage, GPL-family licensing. Nothing to learn from the data model that Kanri's schema does not already do better, and real copyleft exposure if code were ever borrowed.
  • Self-hosted cross-encoder rerankers. Model weights and GPU inference do not belong in a Vercel serverless function. If reranking is needed, call an API or use Claude.
  • An agent framework. LangChain, LangGraph, CrewAI and similar. Kanri's handlers are direct Anthropic SDK calls and are perfectly legible. A framework would add indirection, version churn, and prompt opacity to solve a problem Kanri does not have.
  • A separate vector database. Qdrant, Weaviate, Pinecone. pgvector inside the RLS boundary is both simpler and better aligned with the APPI posture in CLAUDE.md §10. Moving candidate text to a third-party store is a compliance conversation Kanri does not need to have.
09 / Memory discoveries

What the memory ecosystem actually knows

Three transferable insights, in descending order of value to Kanri.

One: facts should be rows with validity intervals, not sentences in a paragraph. Every serious system converged on this. Kanri's prose reconciliation is genuinely differentiated as an output — a senior recruiter's reference note is more useful to read than a fact table — but it is a poor storage format. Storing structured facts and generating the prose from them gives both: the readable note stays, and the facts become queryable, aggregable, and diffable. It also fixes the truncation problem, because a handler can request the eight facts relevant to its task instead of slicing the first 400 characters of a narrative.

Two: memory extraction is a separate step from memory retrieval, and both are separate from consolidation. Kanri currently fuses all three into one refresh-context call that reads 30 interactions and writes a narrative. That is why it is expensive, why it must be manual, and why it truncates. Splitting them — extract facts on interaction insert, retrieve relevant facts at query time, consolidate periodically via cron — makes each step cheap enough to run automatically.

Three: the interesting benchmark is temporal, not semantic. The 15-point gap between Graphiti's 63.8% and Mem0's 49.0% appears specifically on facts that change over time. Recruiting is almost entirely facts that change over time: salary expectations, notice periods, availability, interest level, competing processes, who the hiring manager is. Kanri is operating in the regime where temporal modelling matters most, which is a reason to take §L1 seriously rather than filing it as sophistication.

10 / Graph or no graph

Does Kanri need a graph database?

No. And this deserves a direct answer because "knowledge graph" is the most seductive phrase in this ecosystem and adopting one would be a serious, hard-to-reverse mistake for a product at Kanri's stage.

The argument for a graph is that recruiting is relational: candidate → company, candidate → process → requisition → client → contact, placement → hiring manager. The argument against is that Kanri already has those relationships as foreign keys in a relational database, correctly modelled, with RLS enforcing team scope on every one of them. A graph database would re-encode existing structure in a second store that must be kept in sync — the exact "permanent sync liability" argument that settled the displacement question in CLAUDE.md §1, applied internally.

Graph databases earn their keep on unbounded-depth traversal over schemas that change shape. Kanri's traversals are shallow and known in advance: two or three joins, all of them written already. Postgres does this well. The thing Kanri lacks is not graph traversal — it is temporal fact storage and semantic retrieval, and both are ordinary tables plus an index.

The one relationship capability genuinely worth adding is not a graph at all. It is a candidate_company_history view that already exists implicitly in candidate_roles: who worked where, when. That single relation answers the highest-value BD question in the Stage 1 report — "your placed candidate is now a hiring manager at a company you don't cover" — with one query and no new infrastructure.

11 / Search and retrieval

The concrete Wave 2 design

Constraints established by this audit, in order of how much they narrow the design:

  1. No BM25 extension exists on Supabase. pg_search and pg_textsearch are both unavailable.
  2. Built-in Postgres FTS cannot tokenize Japanese.
  3. PGroonga handles Japanese, English, and mixed text in one index, with its own scoring.
  4. pgvector 0.8.0's iterative scans matter because every Kanri query filters by team_id, which is precisely the over-filtering case those scans were added to fix.

Which produces one obvious architecture:

lexical    → pgroonga index over notes_interview, ai_context,
             full_notes, summary  (handles JP + EN in one index)
semantic   → pgvector HNSW over contextual-prefixed chunks
fuse       → reciprocal rank fusion, ~15 lines of SQL
filter     → team_id, status, language level, comp band — pushed
             down before ranking, iterative scans on
rerank     → Claude over the top ~30, scoring with stated reasons
             (produces the explainability payload for free)

The reranking step is where Kanri gets something competitors buy separately. A Cohere or Voyage reranker returns a better ordering and a number. Claude returns a better ordering, a number, and the sentence explaining it — which CLAUDE.md's explainability rule requires anyway, and which recruiters need in order to trust the result. Paying a reranking vendor and then paying Claude again to explain the ranking would be strictly worse.

12 / Japan discoveries

Four Japan-specific findings

Blocker
PGroonga is not optional

Without it there is no Japanese full-text search in Postgres, and Kanri's most valuable content is Japanese interview notes. PostgreSQL-licensed, available on the project, one statement to enable. This is the single most important technical finding in the audit.

Free state data
Japan ships master data nobody uses

法人番号 Web-API for corporate identity (free application ID, name search, period diffs) and the Digital Agency address registry behind an MIT-licensed TypeScript normalizer. Structurally unavailable to horizontal competitors, who will never localize this deeply.

Measurable
Keigo correctness can be tested, not guessed

The Tohoku University keigo transfer dataset gives 390 native-annotated sentences for honorific conversion. Small, but it turns "does our 推薦文 sound right?" from an opinion into a number — and register errors are precisely the failure mode Headhunt.AI names for generic models.

Open question
Japanese-specialist embeddings may not win here

Ruri-base beats mE5-large on JMTEB. But Kanri's notes code-switch mid-sentence between Japanese and English, which is the case neither benchmark measures. Test on real notes before choosing.

One note on what not to do. The Japanese NLP ecosystem is rich and almost all of it is Python, built for research pipelines rather than serverless request handlers. The temptation is to pull in morphological analysis, named-entity recognition, and reading estimation because they exist and are good. Resist it: PGroonga covers indexing, Claude covers extraction and generation, and the government APIs cover canonical identity. That is the whole Japan stack Kanri needs.

13 / 10x opportunities

Three that change the product, not the velocity

  1. X1
    The queryable fact ledger

    Structured, bi-temporal facts extracted from every interaction — subject, predicate, value, valid_from, valid_to, source. Kanri stops being a system that writes notes and becomes one that knows things.

    What it unlocks that no competitor offers: "which candidates raised their salary expectation this quarter?" · "which clients' requirements have drifted since intake?" · "show me everyone who said they'd move for the right role, six months ago, who hasn't been contacted since." None of these are answerable by transcript storage, summarization, or semantic search. They need facts with dates.

  2. X2
    The event spine, fully exploited

    Once pgmq plus pg_cron plus pg_net exist for context refresh, every other proactive feature in the Stage 1 roadmap becomes a queue consumer rather than a project: pre-meeting briefs that fire themselves, offer-stage watches, competitive clocks, weekly re-engagement lists, job-change detection. Wave 5 stops being a wave and becomes a series of small additions to infrastructure that already runs.

    This is the difference between a product that responds to clicks and one that arrives before the recruiter asks — and the audit's finding is that the gap between them is one migration, not one quarter.

  3. X3
    Explainability as a byproduct rather than a feature

    If retrieval runs through typed tools and reranking runs through Claude with stated reasons, then every AI surface can already name the records it read and why they ranked where they did. The explainability panel stops being something to build and becomes something to display.

    Against Bullhorn's opaque hire-likelihood model, and under 職業安定法 Art. 5-4, that is a commercial asset rather than a compliance cost — and it costs nothing extra if the retrieval architecture is designed for it from the start. If it is not, retrofitting explainability across 41 handlers is a large and thankless project.

14 / Architectural implications

Does the current architecture need to change?

Less than the ecosystem's marketing would suggest, and more than Stage 1 assumed. Four changes, all inside Postgres.

  • Add an event/queue layer. pgmq plus pg_cron plus pg_net. Unlocks: automatic memory, automatic embedding, all proactive features. This is the one genuinely new architectural component and it is entirely in-database.
  • Add a retrieval layer. pgvector and PGroonga indexes plus an RRF fusion function exposed as a single SQL function. Handlers call one retrieval function instead of hand-writing selects. Same shape as the context loader, and the two should be built together.
  • Add a fact layer beside the narrative. A *_facts table with validity intervals. The prose ai_context stays as a generated view over the facts, which fixes truncation at the same time: handlers request facts by relevance instead of slicing a paragraph.
  • Do not add: a graph database, a vector database, an agent framework, a Python service, or an ML model server. Every one of these was considered and rejected on evidence, not aesthetics.

The data model change worth flagging: the ai_context column becomes derived rather than authoritative. That is a meaningful shift and it should be a deliberate decision recorded in CLAUDE.md, not something that happens gradually while nobody is looking.

Security notes

  • pg_net and credentials. Any URL or key used by a database trigger must live in Supabase Vault, never inline in a migration. Migrations are committed to git.
  • pg_net is fire-and-forget. Responses are not guaranteed. Durability comes from the pgmq visibility timeout, not the HTTP call. Designing as if pg_net were reliable produces silent data loss.
  • Service-role reach. A queue worker invoked from Postgres runs outside a user session. It must re-establish team scope explicitly, or RLS provides no protection. This is the most likely place for a cross-team data leak to be introduced.
  • Never generate raw SQL from user text. Beyond the accuracy evidence in §L2, it is an injection surface pointed directly at candidate PII, which under the 2026 APPI amendment carries a surcharge regime for breaches affecting more than 1,000 individuals.
  • Keeping candidate text in Postgres is a compliance feature. Shipping it to a third-party vector service is a data-transfer question Kanri currently does not have to answer. That is a reason to prefer pgvector beyond convenience.

18 / Ten questions

Direct answers

1. The five most interesting technologies discovered?

PGroonga (Japanese FTS inside Postgres) · pgmq (durable queue inside Postgres) · pg_net (async HTTP from SQL) · pgvector 0.8.0 iterative scans (filtered vector search that actually works under RLS) · Graphiti's bi-temporal model (as a concept).

2. The five most interesting product concepts?

Bi-temporal facts with validity intervals · contextual retrieval (context prepended before embedding) · semantic layer instead of text-to-SQL · append-only memory with reconciliation at read time · self-editing recruiter-level memory blocks.

3. The single technology to investigate further?

PGroonga. It is a hard blocker on Japanese search, it is already available, and validating it takes an afternoon: enable it, index real Japanese interview notes, run queries a recruiter would actually ask.

4. The single product idea to investigate further?

The bi-temporal fact ledger. It is the difference between a product that stores notes and one that knows things, and it is the only idea here that competitors cannot copy by shipping a feature — they would need the history.

5. Anything that could fundamentally change the architecture?

Yes — the in-database event spine. It changes Kanri from request-response to event-driven without adding a single service, and it is the precondition for every proactive feature in the roadmap.

6. Anything that creates a moat?

The fact ledger, because it accrues and cannot be backfilled. Also 法人番号 identity resolution, which is small but structurally unavailable to horizontal competitors. Note that no technology here is a moat — pgvector is available to everyone. The moat is the accumulated, reconciled, timestamped history it stores.

7. Anything substantially better for Japanese recruiters?

PGroonga, decisively — it is the difference between working and broken. Then 法人番号 and address normalization for entity resolution, and the keigo evaluation set for measuring 推薦文 register quality rather than guessing at it.

8. Anything Spott or Headhunt.AI are unlikely to have?

Bi-temporal facts over a two-year recruiter relationship: Spott's Conversation Memory captures and summarizes; it does not model change over time. Japanese government master-data integration: too narrow for a horizontal product, and Headhunt.AI stops at first reply so it never needs client identity. And ranking explanations produced by the ranker itself rather than bolted on afterwards.

9. What should we absolutely not incorporate?

Any graph database. Any separate vector database. Any Python memory framework as a dependency. Any agent framework. JavaScript Japanese tokenizers. OpenCATS. Self-hosted rerankers. Each was genuinely considered; each fails on architectural fit rather than quality.

10. What to investigate next, before writing code?

Three things, in order: (a) enable PGroonga on a branch and test Japanese retrieval against real notes; (b) test two or three embedding models on genuinely code-switched Kanri notes rather than trusting JMTEB; (c) prototype the fact-extraction prompt on twenty real interactions and check whether the facts it produces are ones a recruiter would actually want queried.

19 / Next steps

Recommended sequence

  1. Spike PGroonga on a Supabase branch. Half a day. Enable it, index notes_interview, run ten real recruiter queries in Japanese and English. This either confirms the Wave 2 design or invalidates it before anything is built on top.
  2. Embedding model bake-off on real notes. Half a day. Ruri, multilingual-e5, and one Anthropic-adjacent option against genuinely code-switched Kanri content. The benchmark tables do not measure Kanri's actual data.
  3. Prototype fact extraction on twenty interactions. One day, prompt only, no schema. The question is whether extracted facts are things recruiters would query — if they are not, the ledger is sophistication rather than leverage and should be dropped.
  4. Then start Wave 1 with the extension set and the generic job queue, informed by all three.

Total: roughly two days of investigation that de-risks the two largest architectural commitments in the roadmap. Given that Wave 2 as originally specified contained a silent Japanese-language failure, that seems a reasonable trade.
